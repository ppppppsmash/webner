### 4.3 技術構成（2026-11-11 確定分）

| 項目 | 内容 |
|---|---|
| フレームワーク | **Next.js**（App Router 想定） |
| 公開側 URL | `https://xxxxx.com/`（ドメイン未定） |
| 管理画面 URL | `https://xxxxx.com/management/` 配下 |
| 画面の分離 | 同一 Next.js アプリ内で、**middleware** により `/management` 配下を管理画面として分離し、未ログイン時はログイン画面へリダイレクト |
| 認証 | 2方式を併用: ① **メールアドレス（Gmail）＋パスワード** ② **Google アカウントでのワンボタンログイン**（Google OAuth） |
| 管理アカウント数 | 10 個以内。**招待制**（既存の管理者が招待した人だけ登録できる。自由登録なし） |
| 商品説明 | リッチテキストエディタ |
| 動画 | ファイルアップロード＋外部 URL 埋め込みの両対応 |
| 既存ショップへのリンク | あり。将来外せるよう設定で ON/OFF |
| 初期データ | ある程度開発が進んでから、**依頼元が管理画面から**既存商品（約37点）を投入する |
| 管理画面 UI 言語 | 繁体字中国語（zh-TW） |
| DB / ストレージ / ホスティング | 未定。推奨案は 4.4 参照 |

- 認証ライブラリは Auth.js（NextAuth）の Credentials プロバイダ＋Google プロバイダを想定

#### 招待制の流れ（案）

1. 既存の管理者が管理画面で招待したい人の **メールアドレスを登録**（許可リスト）
2. 招待された人には2つの入り方がある
   - **Google ワンボタンログイン**: 登録済みメールと一致する Google アカウントならそのまま入れる（パスワード不要）
   - **メール＋パスワード**: 招待メールのリンクからパスワードを設定して入る
3. 許可リストにないメールは、Google ログインしても弾く
4. 管理者はいつでも許可リストから削除できる（＝アカウント無効化）

- メリット: 自由登録が存在しないので不正登録のリスクがない。10 人以内の小規模運用に向く
- 補足: 全員が Google ログインを使うなら、パスワード方式はなくても運用できる（パスワード再設定などの機能が不要になり、実装も安全性も楽になる）。要望どおり両方実装するが、将来パスワード方式を外す選択肢は残しておく

### 4.4 インフラ推奨案（2026-11-11 時点、未確定）

「スペックが弱くなく、安い」構成として以下を推奨する。料金は概算で、契約時に公式サイトで要確認。

| 役割 | 推奨 | 理由 | 概算月額 |
|---|---|---|---|
| ホスティング | **Vercel Pro** | Next.js の開発元。設定がほぼ不要で、画像最適化・プレビュー環境付き。無料の Hobby プランは商用利用不可のため Pro が必要 | 約 US$20 |
| DB | **Neon（PostgreSQL）** | サーバーレス Postgres。商品37点程度なら無料枠でも足りるが、本番は有料プランで安定させる | 無料〜約 US$19 |
| 画像・動画ストレージ | **Cloudflare R2** | S3 互換で **転送量（egress）が無料**。動画配信で転送量課金されないのが最大の利点。10GB まで無料 | ほぼ無料〜数ドル |
| 動画配信（任意） | Cloudflare Stream | 画質自動切替・変換が必要になった場合のみ追加 | 使った分だけ |

- 合計: **約 US$20〜40 / 月** 程度

#### 台湾ドル換算の月額目安（2026-11-14 時点、1 USD ≒ 32 TWD）

前提: 商品約 40 点、画像約 200 枚（1〜2 GB）、動画約 10 本（5〜10 GB）、月 1 万訪問。料金はブログ等の二次情報を含むため契約前に公式ページで要確認。

| 役割 | サービス | 料金の仕組み | 月額の目安 |
|---|---|---|---|
| ホスティング | Vercel Pro | 月 US$20（1 席、US$20 分の利用枠込み）。無料の Hobby は商用不可 | NT$640 |
| データベース | Neon（PostgreSQL） | 従量制。計算 US$0.106/CU 時間、保存 US$0.35/GB 月。小規模なら月 US$5〜15 | NT$160〜480 |
| 画像・動画 | Cloudflare R2 | 保存 US$0.015/GB 月、10 GB まで無料。配信の転送量は無料 | NT$0〜50 |
| ドメイン | — | 年 NT$400〜1,000 | 月換算 NT$35〜85 |
| Google ログイン | Google Cloud | 無料 | NT$0 |
| **合計** | | | **約 NT$850〜1,250 / 月** |

- 別案: Supabase Pro（月 US$25、DB 8 GB・ファイル 100 GB・転送 250 GB 込み）＋ Vercel Pro ＝ 約 NT$1,450 / 月。契約先は減るが、動画の転送量超過は US$0.09/GB
- 開発・検証中は各社の無料枠（Neon Free、R2 10 GB、Vercel Hobby）で費用ゼロ
- AWS（RDS ＋ S3）は最小構成でも DB だけで月 US$12〜15、S3 の転送 US$0.09/GB が加わり、この規模では割高
- 画像は Next.js の `next/image` で最適化、動画は R2 から直接配信する想定
- より安くする代替案: Cloudflare だけで構成（Workers ＋ D1 ＋ R2、約 US$5/月）。ただし Next.js を Workers で動かす（OpenNext）には互換性の制約があり、開発工数が増えるリスクがあるため第一候補にはしない
- 全部入りの代替案: Supabase（DB＋認証＋ストレージ）。便利だがストレージの転送量に課金されるため、動画を多く置くなら R2 の方が安い

#### インフラ決定のタイミング（2026-11-11 決定）

インフラの選定・契約は **開発の最後** に行う。それまでは以下のローカル構成で開発し、本番環境は差し替えるだけで済むように作る。

| 役割 | 開発中（ローカル） | 本番（最後に決定） |
|---|---|---|
| DB | ローカル PostgreSQL（Docker）または Neon 無料枠 | Neon 有料 等 |
| 画像・動画 | ローカルの `uploads/` ディレクトリ、または S3 互換のローカルサーバー（MinIO） | Cloudflare R2 等 |
| ホスティング | `next dev` | Vercel 等 |
| Google ログイン | `http://localhost:3000` をリダイレクト先として Google Cloud Console に登録 | 本番ドメインを追加登録 |

差し替えを楽にするための実装ルール:

- DB は **PostgreSQL（確定）**。DB アクセスは ORM 経由にし、接続先は環境変数 `DATABASE_URL` だけで切り替える。ORM は **Drizzle（確定）**。比較は下記
- ファイル保存は「ストレージインターフェース」を1枚挟み、ローカル保存と S3 互換（R2）の実装を切り替えられるようにする
- 本番でしか動かない設定（ドメイン、OAuth の本番リダイレクト先、ストレージの公開 URL）はすべて環境変数にまとめる
- 開発中から **PostgreSQL** を使う（SQLite で始めると本番移行時に差分が出るため）

#### ORM の比較（Prisma vs Drizzle）

| 観点 | Prisma | Drizzle |
|---|---|---|
| スキーマの書き方 | 独自の `schema.prisma`。読みやすい | TypeScript で定義。SQL に近い |
| クエリ | 独自 API。簡単だが複雑な SQL は書きにくい | SQL に近い API。JOIN や集計を細かく制御できる |
| サーバーレス（Vercel）との相性 | 近年のバージョンでバイナリエンジン不要になり改善 | 軽量で起動が速い。Neon のサーバーレスドライバと相性がよい |
| マイグレーション | 成熟。`prisma migrate` | `drizzle-kit`。十分実用的 |
| データ閲覧ツール | Prisma Studio（優秀） | Drizzle Studio（あり） |
| Auth.js アダプタ | あり | あり |
| 本人の経験 | — | kh-project で使用済み |

**Drizzle に決定（2026-11-11）**。この規模（商品数十点の CRUD）ではどちらでも困らないため、既に使った経験があり、サーバーレスで軽く、SQL を素直に書ける Drizzle を選ぶ方が学習コストと運用リスクが小さい。Prisma を選ぶ場合の利点は Prisma Studio と独自スキーマの読みやすさだが、決定打にはならない。

#### 進め方

1. 優先 1 は 2026-11-14 に実装済み（マイグレーション 0001〜0003。`is_published` は `visibility` に移行済み）
2. 優先 2 は依頼元に「複数分類が要るか」「規格違いを 1 商品にまとめるか」を確認してから着手する（6. 参照）
3. 優先 3 は初期データ投入の規模が見えてから判断する。SHOPLINE の CSV エクスポートが使えれば取り込みを優先する

#### SHOPLINE からの商品エクスポート手順（2026-11-14 調査、依頼元に依頼する内容）

1. 管理画面の左メニュー「商品及分類 > 商品」を開く
2. 商品一覧でチェックボックスで商品を選ぶ（全件なら全選択）
3. 一覧上部の「匯出」→「已選取 n 件商品」を選ぶ
4. Excel（.xlsx）のダウンロードリンクが、ログイン中アカウントのメールに届く（画面で直接ダウンロードはされない）
5. 処理状況は「報表及分析 > 大量作業進度」で確認できる

- 書き出されるのは一括更新用のファイルで、商品代碼（handle）、商品名（英文・繁體中文）、商品摘要、商品描述（HTML）、価格・在庫などの列が入る
- 分類と画像が含まれない版があるという報告あり（一括更新テンプレートには Images 列がある）。まず 1 回エクスポートして列構成を確認する
- Excel で中国語が文字化けする場合は Numbers で開くか、Excel の「データ > テキスト/CSV から」で UTF-8 を指定する
- 画像が含まれない場合は、商品ページの画像 URL（shoplineapp.com の CDN）を収集するか、依頼元から画像フォルダをもらう
- 依頼元には「商品を全選択して匯出し、届いた Excel をそのまま送ってほしい」と依頼する。1 ファイルあれば取り込みスクリプトの設計ができる
- 参考: [Product List](https://support.shoplineapp.com/hc/en-us/articles/360032158371-Product-List-Products-Categories)、[How to Bulk Update Products](https://support.shoplineapp.com/hc/en-us/articles/360019883172-How-to-Bulk-Update-Products)

## 8. 開発環境メモ

### セットアップ（ローカル）

```bash
pnpm install
cp .env.example .env          # AUTH_SECRET は `openssl rand -base64 32` で生成して記入
docker compose up -d          # PostgreSQL 17（localhost:5432, user/pass/db = webner）
pnpm db:migrate               # drizzle/ 配下のマイグレーションを適用
pnpm seed:categories          # README 4.5 の初期カテゴリを投入
pnpm seed:admin               # .env の SEED_ADMIN_EMAIL / PASSWORD で最初のオーナーを作成
pnpm dev                      # http://localhost:3000/management
```

| スクリプト | 内容 |
|---|---|
| `pnpm dev` / `pnpm build` / `pnpm start` | Next.js |
| `pnpm typecheck` | `next typegen` ＋ `tsc --noEmit` |
| `pnpm lint` | ESLint（React Compiler ルール含む） |
| `pnpm db:generate` / `db:migrate` / `db:push` / `db:studio` | Drizzle Kit |
| `pnpm seed:admin` / `pnpm seed:categories` | 初期データ投入 |
| `pnpm e2e` | Playwright によるスモークテスト（dev サーバー起動中に実行。ログイン→分類→商品→設定→招待まで一通り操作し、`e2e/output/` にスクリーンショットを保存） |

Google ログインを使う場合は Google Cloud Console で OAuth クライアントを作り、`AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET` を `.env` に設定する。リダイレクト URI は `http://localhost:3000/api/auth/callback/google`（本番はドメインを追加）。未設定の間はログイン画面に Google ボタンが出ない。

### 公開サイト（ギャラリー）の構成と設計（2026-11-12 時点）

参考サイト（WADI / etherischeoele.de）の構成「上部バー → ロゴ＋ナビ → ヒーロー → ブランド紹介 → おすすめ → ベストセラー → 大きなフッター」を踏襲しつつ、口コミ・B2B・ニュースレターなど本件に不要な要素は省いた。

| パス | 画面 |
|---|---|
| `/` | Cookie → Accept-Language の順で言語を判定し `/{locale}` へリダイレクト |
| `/{locale}` | トップ（ヒーロー、ブランドストーリー、分類タイル、推薦商品、最新上架、価値観、商店バナー） |
| `/{locale}/products` | 商品一覧（左に分類ナビ、スマホはチップ横スクロール） |
| `/{locale}/categories/{slug}` | 分類別一覧（大分類は小分類の商品も含む） |
| `/{locale}/products/{slug}` | 商品詳細（画像ギャラリー、容量・分類、購買連結、リッチテキスト説明、影片、関連商品） |
| `/{locale}/about` | ブランドページ |

locale は `de` / `en` / `zh-TW` / `zh-CN`。文言は `lib/i18n/public/*.ts` に 4 言語分（型 `PublicDictionary`）。商品・分類名は DB の jsonb から `pickText()` で取り出し、未入力の言語はドイツ語へフォールバックする。

#### デザイン方針「ドイツのブランドショップ」（2026-11-12 改訂）

最初の案（紙色＋苔色＋琥珀の雑誌風）は依頼元の意図と合わなかったため、WADI に加えて Primavera / Taoasis / Oshadhi / Dr. Hauschka / Weleda / farfalla を調べ、ドイツのブランドサイトに共通する作法に合わせて作り直した。

| 要素 | 決定 |
|---|---|
| 配色 | 白背景、ブランド色は紺（`--brand` oklch 0.31/0.065/272 ≒ #252d51）、淡い水色（`--tint`）をナビ帯・フッター帯・バッジに。本文は墨色、補助文はグレー。琥珀は使わない（ボトル写真に任せる） |
| フォント | 見出し Lora（クラシックなセリフ）、本文 Libre Franklin。中国語は Noto Serif TC / Noto Sans TC |
| ヘッダー | 3 段: 紺の細帯（キャッチ＋言語切替）→ 白地にロゴ・検索窓・商店ボタン → 水色の帯にメニュー（Produkte はホバーで分類ツリーのドロップダウン） |
| ロゴ | 実物のパッケージに合わせ、小文字の太いサンセリフ「webner」＋小さな「GERMANY」 |
| トップ | 全幅写真のヒーロー（管理画面の設定で写真を登録。未登録時は紺のグラデーション）→ 信頼アイコン 4 つ → 中央揃えのブランド宣言 → 推薦商品 → 分類バナー（水色地）→ 最新上架 → 水色の商店案内帯 → 水色フッター |
| 商品カード | 白地、正方形の写真、中央揃えの商品名、分類と容量、「DETAILS」リンク。推薦品は水色の「TOP」バッジ。ホバーで 2 枚目の写真 |
| ボタン | 角のほぼない長方形。紺塗り／紺枠／白塗り（ヒーロー用） |
| 一覧・詳細 | 一覧は中央揃えの見出し＋左に分類ナビ。詳細は左に写真とサムネイル、右に分類・セリフの商品名・容量・紺の「Im Shop ansehen」・説明 |
| 演出 | 控えめ。ヒーローの段階フェードとスクロール時の 1 回だけの表示のみ |

トークンは `app/globals.css` の `.site` に定義し、Tailwind には `bg-paper` / `bg-paper-2` / `text-ink` / `text-ink-2` / `bg-brand` / `bg-brand-deep` / `bg-tint` / `bg-tint-soft` / `border-line` として公開している。管理画面（shadcn のテーマ）とは分離。

#### キャッシュ

公開ページのデータ取得（`lib/queries/public`）はすべて `"use cache"` ＋ `cacheTag`（`products` / `categories` / `settings`）。管理画面の保存・削除・公開切替の Server Action が `updateTag` を呼ぶので、保存した瞬間に公開側へ反映される。
